# 단타 알림·자동매매 시스템 (토스증권 Open API)

토스증권 Open API 로 1분봉·현재가를 30초마다 읽어 VWAP·RVOL·선행 바스켓 조건으로
**매수 / 손절 / 익절 신호**를 만들고 텔레그램으로 보낸다. 감시 종목은 백오피스 화면에서 지정한다.
신호마다 **공용 가상 장부**가 실계좌와 격리된 채 가상으로 사고팔아 모의매매 기록을 쌓는다. 실제 주문은 **계정별 live** 뿐이다 —
백오피스에 Google 로 로그인한 허용 계정이 자기 API 키(DB 에 암호화)를 넣고 live 스위치를 켜야 그 계정 계좌로 나간다.

| 키 | 어디에 | 쓰임 |
|---|---|---|
| 공용 토스 키 · 공개 텔레그램 | `.env` | 시세·캘린더 조회, 공용 가상 장부, 공용 채널(시장 신호·시황·시스템·가상매매·성적표) |
| 계정별 토스·Binance·텔레그램 키 | MySQL `alert_account_keys` (AES-256-GCM, 마스터 키는 `.env`) | 그 계정의 live 주문과 그 계정 텔레그램 알림(주문·체결·실패·일일 성적) |

| 구성 요소 | 실행 | 역할 |
|---|---|---|
| 통합 실행 | `python run.py` | 아래 워커·백오피스를 자식 프로세스로 띄우고 지킨다 — 비정상 종료·멈춤이면 다시 켜고, 백오피스 '운영' 화면이나 다른 콘솔의 `python run.py status / start / stop / restart <서비스>` 로 제어 (5절) |
| 엔진 워커 | `run_engine.py` | 30초 폴링 → 지표 → 상태기계 → 텔레그램 알림 → (자동매매) |
| 백오피스 | `run_backoffice.py` | http://127.0.0.1:8000 — Google 로그인(허용 계정만) 뒤 **홈(SOXX 매크로)**·종목·상태·신호 이력·자동매매·내 API 키·계정·운영 |
| 매크로 수집 | `run_macro.py` | 미국·일본 금리·환율·국채·SOXX/SPY 시계열, BOJ 기준금리·일본 CPI·DRAM 현물가·반도체 EPS 추정치, 이벤트 캘린더와 결정 결과를 모아 홈 화면을 채운다 (7.1절). 알림 없음 |
| Binance 워커 | `run_binance.py` | 20초 폴링 → 5분봉 ETC 급락 매수 후보 · 4시간봉/일봉 BTC 급등 추종 · 일봉 ETC 급락 추종 숏 · **거래대금 상위 30 코인 급변 감시**(급등은 가상 장부 소진 숏) → 텔레그램 (토스 엔진과 독립, 3.5절 · 자동매매 dry/live 는 3.6절) |
| MySQL | 이미 쓰는 서버 | `alert_*` 테이블. 프로세스들이 공유하는 유일한 통로 (계정·세션·암호화된 키·서비스 상태 포함) |

## 1. 동작 원리

### 1.1 신호 흐름

```
토스 API(공용 키) ──(1분봉·현재가)──▶ 엔진 ──▶ 지표 ──▶ 상태기계 ──▶ Signal ──▶ Dispatcher ──▶ 공개 텔레그램
                                          │                                           └──▶ MySQL alert_signal_log
                                          ├──▶ 공용 가상 장부 실행기 ──▶ DryRunBroker ──▶ alert_orders (account_id NULL) ──▶ 엔진 보유
                                          └──▶ (AUTOTRADE_MODE=live) 계정별 실행기 ──▶ 정책 ──▶ 그 계정 키의 토스 주문 ──▶ 그 계정 텔레그램
```

- **지표**는 완성된 봉만 쓴다. 진행 중인 마지막 봉은 거래량이 부분값이라 뺀다.
- **RVOL(상대 거래량)**: 같은 현지 시각의 과거 8세션 중앙값 대비 배수. 표본이 없으면 직전 정규장 20봉 평균 대비.
- **VWAP·세션 정점 RVOL**: 당일 정규장 봉을 누적해서 계산한다(120봉 창이 아니다).
- **매수 신호(🔵)**: 선행 바스켓 방향 OK + RVOL 2.0 돌파 + 신호봉 종가가 VWAP 밴드 위 + 강봉(종가가 봉 상단 절반). 정규장 봉, 개장 10분 뒤부터 4시간 안에서만.
  **추격 배제**: 오늘 갭 +1% 이상, 전일 종가 대비 +3% 이상, 전일 +2% 이상, 5세션 +8% 이상, 20세션 평균 위 +10% 이상인 자리의 돌파는 신호를 내지 않는다
  (2026-09-17 3개월 재생에서 두 시장 모두 다음날까지 손실이었던 유일하게 일관된 필터). 일봉은 세션당 한 번 받고, 없으면 그 항목은 건너뛴다.
- **보유 중**: 손절(-5%) > 목표 +1% 익절 > 신호봉 저점/밴드 이탈 매도 > 거래량 소진 익절(수익 중일 때만) > 불타기 > 일부 익절 검토 > 판단 애매 > 마감 30분 전.
- **엔진이 보는 보유는 공용 가상 장부뿐이다.** 실계좌는 읽지 않는다. 가상 장부는 확정 매수 신호마다 가상 매수하고(한도 없음), 청산 신호에 전량 가상 매도한다.
  그래서 '내 보유' 로 돌던 기능 — 평단 기준 손절 한도, 🎉✅ 청산 완료, 📈 오늘 가상매매 성적, 시황의 '가상 보유', 미청산 반복, 페어 차단 — 은 전부 가상 장부 기준이다.
  보유 중에만 감시하는 종목(SOXL·SOXS 등)은 가상으로 사지 않으므로 감시되지 않는다.
- **신호 포지션**: '매수하세요'(확인 항목 — EMA 정배열·선행 모멘텀 — 을 다 채운 신호)가 나가면 가상 장부에 보유가 없어도 그 종목은 곧바로 **보유**로 관리한다 — 다음 알림은
  매수 대기·취소·만료가 아니라 추가매수·익절·손절이다. 손익과 손절 한도(-5%)의 기준은 **신호가**이고(본문 첫 줄 `신호가 X 대비 ±y%`), 가상 평단
  손익은 장부 줄에 붙는다(미보유면 `가상 미보유 — 신호가 기준`). 확정 청산 신호(손절·매도·전량 익절·마감 정리)가 나가면 신호 포지션은 끝난다
  — 가상 보유가 남아 있으면 가상 매도가 체결될 때까지 청산대기(반복), 없으면 곧바로 관망. '매수 대기하세요' 는 확인 항목이 모자란 신호에만 쓰고, 채워지면 '매수하세요' 로
  승격(그때 신호 포지션), 아니면 '⚪ 매수 대기 취소/만료' 로 끝난다.
- **신호 모의 성적**: 신호 포지션이 닫힐 때마다 신호가 → 청산 신호 시점 가격의 손익이 `signal_trades.csv` 에 남고, 장 마감 때
  `📈 오늘 신호 성적`(청산 건수·승률·평균·합계·손익비·건별 줄·아직 열린 신호)이 온다. 체결·수수료 없는 모의 성적이고 건당 같은 금액 기준이다.
  가상 장부의 체결 기준 청산은 따로 `📈 오늘 가상매매 성적`(trade_log.csv)이다. 둘 다 공용 채널로 간다. 계정 live 의 실제 체결 성적(`📈 오늘 성적`)은 그 계정 텔레그램으로만 간다.

### 1.2 종목별 상태기계

`관망 → 진입대기(매수 대기 알림) → 보유(확정 매수 신호 = 신호 포지션, 또는 가상 보유 확인) → 청산대기(매도 알림) → 관망(확정 청산 신호 · 가상 보유 소멸)`.
확정 매수 신호는 곧바로 보유(신호 포지션)다. 그 밖의 전이는 시간이 아니라 **가상 장부의 보유 변화**로 일어난다 — 가상 보유가 남아 있으면
같은 청산 알림이 쿨다운 간격으로 반복되고, 가상 보유 없이 신호 포지션만 열려 있으면 확정 청산 신호 한 번으로 끝난다(반복할 대상이 없다).
가상 보유가 사라져도 신호 포지션이 열려 있으면 관망으로 가지 않는다. 상태·손절선·타이머·신호 포지션은 MySQL 에 저장되어 재시작해도 이어진다.

### 1.3 알림 등급과 쿨다운

| 등급 | 알림 | 쿨다운 |
|---|---|---|
| action | 🔵 매수 · 🔴 손절/매도 · 🟢 전량 익절 · 🔵 추가매수 · 🟠 마감 정리 · 📤✅🚫⛔ 주문 관련 · 🔵 급락 매수/추가매수 후보 · 🔵 추종 매수 후보 · 🔴 추종 숏 후보 · 🔴 손절/🟢 전량 익절·정리(코인 신호 포지션 종료) · 📥📤 가상 포지션 진입/종료(Binance) | 15분 (주문 관련은 없음, Binance 급락 매수 60분 · 추종은 보유 한도 7일/20일) |
| review | 🔵 매수 대기(확인 항목이 모자란 신호와 그 반복) · 🔴 매도 대기(얕은 이탈 신호와 미청산 반복) · 🟡 절반/1/3 익절 검토 · ⚪ 매수 대기 취소/만료 · ⚪ 청산 신호 해제 · 🎉✅ 청산 완료 · 📈 급등 확인 · 📉 급락 확인(Binance 추종 관찰) · 🚀 급등 감지(가상 장부 소진 숏 대기) · 💥 급락 감지(관찰) | 45분 / 15분 (Binance 추종은 7일/20일, 급변 감시는 코인당 4시간) |
| info | 📊 시황(30분, KST :00/:30 칸) · 🌙 미국 프리마켓 분석(04:00 ET~개장, 같은 30분 칸, 갭·프리 VWAP·누적 거래량 배수·선행, 매수·매도 판단 없음) · 🔔🔕 장 시작/마감(실제 정규장 시각. 감시는 앞뒤 10분 여유) · 📈 오늘 가상매매 성적 · 📈 오늘 신호 성적(모의, 코인은 자정 KST) · 📈 오늘 성적(계정 live, 그 계정에만) · ⚪ 시스템 | 없음 |

쿨다운 키는 (신호 종류, 종목, 계정)이다. 채널은 등급 필터 없이 전부 받는다.

**알림 경로** — `Signal.account_id` 가 없으면 공용 채널(`.env` 공개 텔레그램)로, 있으면 그 계정의 텔레그램(백오피스 '내 API 키')으로만 간다.
공용 채널은 시장 신호·시황·장 시작/마감·시스템·가상매매 매수 체결/청산 완료·성적표를 장부 줄까지 전부 받는다. 계정 채널은 그 계정의 live 주문 접수(주문번호)·체결(실현손익)·실패·차단·일일 성적만 받는다.
공용 채널에 싣지 않는 것: 기동 알림('감시 시작' — 콘솔·로그 파일에만), 관리 프로세스의 비정상 종료·멈춤 재시작 알림(로그·신호 이력·운영 화면에만), 주문번호, 가상 장부의 주문 접수(접수 즉시 체결이라 체결 알림과 같다)와 매도 체결(다음 사이클의 청산 완료가 수량·평단·청산가·손익을 싣는다).
한국 주식 가격(현재가·기준선·신호가·평단·매도선·체결가)은 원 단위 정수에 천 단위 쉼표(`1,766,000`)로, 미국 주식은 받은 값 그대로 적는다.

### 3.5 Binance 알림 (`run_binance.py` — `binance_crash.py` 급락 매수 5분봉, `binance_follow.py` 추종 알림 상위 봉, `binance_scan.py` 급변 감시)

토스 엔진과 별개의 워커 한 프로세스가 다섯 알림을 돌린다. Binance USDⓈ-M 무기한 선물 봉을 공개 REST 로 20초마다 받아(키 불필요)
**완성봉마다 한 번** 판정한다. 신호는 텔레그램과 `alert_signal_log`(백오피스 '신호 이력')에 남고, 로그는 `binance_signals.log` 다.
자동매매는 3.6절(dry 가상 체결 / live 실제 주문)에 있고, 보유 판단은 없다.

**급락 매수 (5분봉, 기본 ETCUSDT, 종류 `CRASH_BUY`, 같은 심볼 60분 쿨다운)**

| 조건 (모두 만족) | 값 | 상수 |
|---|---|---|
| 급락 | 직전 48봉(4시간) 고점 대비 종가 하락폭 ≥ 기준 ATR × 10 | `CRASH_LOOKBACK` / `CRASH_ATR_MULT` |
| 과매도 | RSI14 ≤ 30 | `CRASH_RSI_MAX` |
| 반전봉 | 신호봉 종가가 봉 범위의 상위 40% (종가 위치 ≥ 0.6) | `CRASH_CLOSE_POS_MIN` |
| 국면 | 4시간봉 EMA9 ≤ EMA21 (하락 배열). 상승 배열이면 로그만 남기고 보류. 급락 조건이 성립한 때만 4시간봉 120개를 받아 판정 | `CRASH_H4_FILTER` / `CRASH_H4_KLINES` |

기준 ATR 은 직전 3일(864봉) ATR14% 의 중앙값(`CRASH_BASE_ATR_BARS`)이라 급락 자체가 ATR 을 부풀리는 효과가 없다.
ETC 라면 대략 -2% 이상의 4시간 낙폭이다. 메시지는 주식 알림처럼 짧다 — `현재가 (4시간 고점 대비 %)` / `RSI · 거래량 배수(직전 60봉 중앙값 대비) · 같은 구간 BTC 하락폭(베타 1.35 보정 기여 ≥ 0.6 이면 "BTC 동반", < 0.25 면 "ETC 단독")` /
`손절(신호봉 종가 −3%, CRASH_STOP_PCT) · 보유 한도(8시간, CRASH_HOLD_HOURS)`. 4시간봉 배열은 조회에 실패했을 때만 적는다. 목표 지정가는 두지 않는다.

근거는 2026-09-15 분석(1분·5분·1시간봉, ETC·BTC 30~90일): 5분봉 ETC 에서 이 트리거가 수수료(왕복 0.1%) 뒤에도
양(+)이었던 유일한 급락 매수 조건이다(37건, 승률 62%, ±8 기준 ATR 브래킷 순평균 +0.31%). 1분봉은 어느 조건도
수수료를 못 넘겼고, 급등 숏은 전부 손실이라 만들지 않았다. 표본 국면이 상승장이었다는 한계가 있다.

- **패턴**: 급등 감지 코인은 72시간 중앙 −11.6%(같은 시각 상위 30 다른 코인 −0.7%), 급락 감지 코인은 −10.3% 흘러내렸다(앞·뒤 두 달 모두). 같은 코인을 아무 시각에 잡아도
  72시간 −7.4%/−9.5% 라 상당 부분은 '급변하는 알트는 흘러내린다'는 성질이다. 다만 급등 뒤 24시간 안에 중앙 +15% 더 올라 곧바로 숏은 손절에 걸린다.
- **방향 비교**: 급락 뒤 숏은 앞 두 달에 좋았던 설정이 뒤에서 나빠져(순위 상관 −0.38) 고를 방법이 없었고, 급등·급락 뒤 롱은 표본 밖에서 이익이 없었다.
  매달 직전 두 달로 설정을 골라 다음 달에 쓰는 전진 검증에서 급등 뒤 숏만 7·8·9월 모두 이익이었고, 그때 뽑힌 진입이 '평균선 아래로 꺾인 뒤'였다.
- **민감도**: EMA10 진입은 뒤 두 달 설정 전부 손실, 대기 12시간은 짧았다. 평균선은 EMA20·50, 대기는 24·48시간이 나았고 손절 폭(7~20%)은 결과를 크게 바꾸지 않았다.
  EMA50·48시간·손절 15~20%·목표 20%·보유 48~72시간 주변 4개 설정은 두 절반·5개월 전부 이익이었다.
- **최종안 성과(표본 안)**: 405건 건당 +1.68%, 중앙 +4.9%, 승률 59.5%, 청산은 목표가 32% · 보유 한도 39% · 손절 29%(손절 평균 −20.5%, 최악 −27.6%).
  포지션당 자본 1/8 기준 최대 낙폭 −14.7%, 비용 2배에도 건당 +1.50%. 설정 선택에 전 기간을 봤으므로 기대치는 전진 검증의 건당 +0.66~1.15% 쪽에 가깝다 — 실험 전략이다.

**신호 포지션 장부 (`binance_book.py`)** — 진입 후보(🔵 급락 매수 · 🔵 추종 매수 · 🔴 추종 숏)가 나가면 신호가·손절선·보유 한도를 장부에
적고, 이후 그 심볼의 알림은 진입이 아니라 관리다: 20초마다 마크 가격을 보고 손절선에 닿으면 🔴 손절하세요(`SELL`), 보유 한도가 되면
🟢 전량 익절/정리하세요(`EXIT_FULL`)를 보내고 장부에서 지운다(숏은 '숏 손절'/'숏 전량 익절'). 본문은 주식 청산 알림처럼 `신호가 X 대비 ±y% (보유 시간)` / 사유 두 줄이다. 코인 시황의 해당 줄은 조건 충족 여부 대신
`🔵 매수 신호 진행 중 — 신호가 X 대비 ±y%, 손절 Z` 로 바뀐다. 5분봉 급락 매수는 60분 쿨다운이 8시간 보유보다 짧아, 신호가 진행 중일 때의
새 급락 봉은 `🔵 급락 추가매수 후보` 로 부르고 손절선·보유 한도를 그 봉 기준으로 갱신한다. 장부는 자동매매(3.6, 가상 장부·계정 live)와 독립이며
`alert_settings.binance_signal_book` 에 저장돼 재시작해도 이어진다. 닫힌 신호의 손익(신호가 → 마크)은 `binance_signal_trades.csv` 에 남고,
날짜(KST)가 바뀌면 지난 하루의 `📈 오늘 코인 신호 성적`(승률·평균·합계·건별·진행 중)이 온다 — 주식의 마감 성적표와 같은 형식.

### 3.6 Binance 자동매매 — 공용 가상 장부 / 계정별 live (`binance_trade.py`, `binance_broker.py`, `ALERT_BINANCE_TRADE_MODE`)

`run_binance.py` 가 진입 후보 알림(🔵 급락 매수 후보 · 🔵 추종 매수 후보 · 🔴 추종 숏 후보)과 급변 감시의 급등 소진 숏(3.5절, 가상 장부 전용)을 체결하고 열린 포지션을 20초마다 감시한다.
**공용 가상 장부**는 모드와 무관하게 늘 돈다 — 공개 시세로 가상 체결(키 불필요, 주문 없음)하고 공용 채널로 알린다.
`live` 모드면 여기에 **계정별 live 트레이더**가 더해져 그 계정 키로 `binance_broker.py` 실제 주문을 내고 그 계정 텔레그램으로만 알린다. 설계는 2026-09-15 레버리지 분석
「청산선 밖의 배율」을 따른다.

| 항목 | 규칙 | 상수 |
|---|---|---|
| 크기 | 명목가 = 전략별 배분 자본 × 유효 배율. 급락 매수 2 · 4시간봉 급등 추종 1 · 일봉 급등 추종 1.5 · 일봉 급락 숏 0.5 (분석의 시작값, 최대 3 / 1.5 / 2 / 1) · 급등 소진 숏 포지션당 0.125. 자본은 가상 장부 `ALERT_BINANCE_TRADE_CAPITAL`, live 는 계정별 | `BINANCE_TRADE_LEVERAGE` |
| 격리 배율 | 진입 크기가 아니라 **청산 거리**를 정한다 (증거금 = 명목 ÷ 배율). 공용 가상 장부는 3배(청산 32.8%), 계정 live 는 **계정마다** 백오피스에서 **1~5배**. 5배가 상한인 이유: 7배면 손절 상한이 8.8% 로 내려가 일봉 롱(−10%)까지 잘린다. 청산 거리 = 100/배율 − 유지증거금 0.5% | `BINANCE_TRADE_EXCHANGE_LEV`, `alert_accounts.binance_leverage`, `BINANCE_LEVERAGE_RANGE` |
| 자금 부족 | 명목가가 그 코인의 주문 단위·최소 명목에 못 미치거나 거래소가 증거금 부족으로 거절하면 **주문 실패가 아니라 보류**로 끝내고 `⏸ 신호 발생 — 자금 부족으로 미체결` 알림을 보낸다(그 장부 채널로). 실패로 세면 3회에 live 스위치가 꺼져, 돈이 없다는 이유로 나머지 전략까지 멈춘다 | `BN_FUNDS`, `binance_trade.INSUFFICIENT` |
| 손절 당김 | 신호 손절이 그 장부 배율의 **손절 상한**(청산 거리 − 5%p)을 넘으면 상한까지 당겨서 주문하고, 그 사실을 그 장부 알림에 적는다. 손절이 청산선에 가까우면 마크 트리거와 시장가 체결 사이의 갭에 청산이 먼저 올 수 있고, 청산은 그 포지션 증거금을 전부 잃는다. 3배는 상한 27.8% 라 아무것도 안 잘리고(공용 채널 그대로), 7배는 8.8% 라 일봉 롱(−10%)·일봉 숏(+25%)이 잘린다 | `BINANCE_STOP_LIQ_MARGIN_PCT`, `binance_trade.stop_for_leverage` |
| 펀딩 게이트 | 진입 시 펀딩이 롱 +3bp/8h 초과, 숏 -3bp 미만이면 크기 절반 | `SURGE_FUNDING_WARN` |
| 체결 | 진입·종료 모두 마지막 체결가 ± 슬리피지(ETC 0.05%, BTC 0.02%), 수수료 테이커 0.05% 편도 | `BINANCE_TRADE_SLIP`, `BINANCE_TRADE_FEE` |
| 손절 | 알림의 손절 참고선(3.5절). **마크 가격**이 닿으면 종료 — 실제 STOP_MARKET(MARK_PRICE) 주문과 같은 조건 | |
| 종료 | 보유 한도(5분봉 8시간 · 4시간봉 7일 · 일봉 20일 · 급등 소진 숏 48시간)에 닿으면 종료. 목표가는 급등 소진 숏만(마크 −20%) | |
| 펀딩 | 정산 시각(00·08·16 UTC)을 지날 때마다 정산된 펀딩비 × 명목가 (롱은 양의 펀딩 지급) | |
| 한도 | 장부마다: 전략·심볼당 열린 포지션 하나(급등 소진 숏은 전략 전체 동시 8개) · 합산 명목 ≤ 자본 합 × 3 · 오늘(KST) 실현손실이 자본 합의 6% 를 넘으면 신규 진입 중단. 자본 합 = 배분 자본 × 전략 수 (가상 5개, live 는 실제로 주문하는 4개) | `BINANCE_TRADE_MAX_OPEN`, `BINANCE_TRADE_MAX_TOTAL_LEV`, `BINANCE_TRADE_DAILY_LOSS_PCT` |
| live 전략 | `BINANCE_LIVE_STRATEGIES` 의 4개만 계정 live 로 주문한다. 급등 소진 숏은 가상 장부 전용 | `BINANCE_LIVE_STRATEGIES` |

포지션은 MySQL `alert_binance_positions` 에만 있어 재시작해도 이어지고(`account_id` NULL = 가상 장부), 백오피스 '자동매매' 화면 아래쪽 표와 텔레그램(📥 진입 · 📤 종료 · ⏸ 보류 · ⛔ 실패,
본문 앞에 `[DRY]`/`[LIVE]`)으로 본다. 진입은 `전략 방향 가격 · 명목` / `손절 · 목표가 · 한도`, 종료는 `전략 방향 가격 · 사유` / `손익 USDT (명목 대비 %)` 두 줄이다(손익은 수수료·펀딩 포함). 같은 심볼의 롱(5분봉)과 숏(일봉)이 동시에 열릴 수 있어 live 는 헤지 모드를 쓴다.
코인 시황(공용 채널)에는 가상 장부의 포지션만 '가상 포지션 (dry)' 아래 `🟢/🔴 심볼 전략 방향  손익% · 손절 · 한도` 로 실린다. 계정 live 포지션은 그 계정의 📥/📤 와 자정(KST) `📈 오늘 코인 성적` 으로만 본다.

**live 동작** — 조건: `.env` `ALERT_BINANCE_TRADE_MODE=live` + 계정의 Binance·텔레그램 키 + 전략별 자본 > 0 + 백오피스 '자동매매' 화면의 **내 Binance live 스위치 ON**.

- 워커는 사이클마다 계정·키·스위치 변경을 확인해 계정 트레이더를 만들거나 치운다(재시작 불필요). 만들 때 그 계정 키로 서버 시각 동기화, 심볼 필터 조회,
  **헤지 모드 · 격리 마진 · 그 계정의 심볼 배율**(`alert_accounts.binance_leverage`, 기본 3배)을 맞춘다. 배율을 바꾸면 키 서명이 달라져 다음 사이클에 트레이더를 다시 만들고 거래소에 새 배율을 건다. 실패하면(키 권한·IP 제한·열린 포지션 때문에 모드 변경 거부) 그 계정에만 ⛔ 알림을 보내고 10분 뒤 다시 시도한다.
  성공하면 그 계정에 가용 USDT 와 자본을 알린다.
- 진입: 명목가를 수량 단위로 내림해 **시장가**(positionSide LONG/SHORT) → 체결 직후 **STOP_MARKET 알고 주문**(`/fapi/v1/algoOrder`, 마크 가격 트리거,
  closePosition). Binance 는 2025-12-09 부터 조건부 주문을 알고 주문 API 로만 받는다. 손절 주문만 실패하면 포지션은 두고 ⛔ 알림 뒤 사이클마다 다시 건다.
- 감시: 손절 주문이 트리거됐으면 그 체결가로 종료 기록, 포지션이 거래소에서 사라졌으면 '직접 종료' 기록, 손절 주문이 취소·만료됐으면 다시 건다.
  보유 한도가 되면 손절을 취소하고 시장가로 닫는다. **스위치를 끄거나 계정이 중지돼도 열린 live 포지션은 닫힐 때까지 감시**한다(새 진입만 막는다).
- 실패: 진입 주문이 3회 연속 실패하면 그 계정의 Binance live 스위치를 끄고 ⛔ 알림. 손익·수수료·펀딩은 가상 장부와 같은 식의 추정값이다(거래소 정산값이 아니다).
- 전환 순서: 가상 장부 기록 검토 → '내 API 키' 에 Binance(선물 거래 권한만)·텔레그램 키 저장 후 연결 확인 → 관리자가 `.env` `live` 로 워커 재시작 → '자동매매' 화면에서 자본 입력 후 스위치 ON.

**dry 확인 절차** — 실제 신호는 드물어서(5분봉 하루 0.5건, 상위 봉 연 수 건) 기다리지 않고 세 단계로 확인한다.

1. 기동 확인. `.env` 에 `ALERT_BINANCE_TRADE_CAPITAL` 을 넣고 워커를 잠깐 돌린다 (가상 장부는 모드와 무관하게 돈다).
   ```bash
   timeout 45 python run_binance.py
   ```
   로그에 `Binance 자동매매 dry: 전략별 자본 … · 합산 명목 한도 … · 일손실 한도 …` 가 찍히고, 공용 채널 시작 메시지에
   `가상매매: 진입 후보 전부 (전략별 자본 …)` 가 오면 설정이 읽힌 것이다. 백오피스 '알림' 의 SYSTEM 행 결과가 `telegram_public: ok` 다.
2. 진입·종료 경로 확인. 과거에 실제로 신호가 났던 봉을 워커에 먹여 알림 → 📥 진입 → 감시 → 📤 종료까지 돌린다. 봉은 Binance 에서 받아 오고,
   체결 시세는 현재 값이며, 확인이 끝나면 강제 종료하고 확인용 포지션 행을 지운다. `--quiet` 를 붙이면 텔레그램 대신 콘솔에 찍는다.
   ```bash
   python check_binance_dry.py crash "2026-09-14 07:15"
   ```
   사양별로 검증된 과거 사례: `crash "2026-09-14 07:15"` · `surge_4h "2026-09-05 21:00"` · `surge_1d "2026-09-03 09:00"` · `crash_1d "2026-06-12 09:00"`
   (모두 KST, 신호봉 시작 시각). 다른 시각을 주면 "그 봉은 신호 조건이 아니다" 로 끝난다. 이 도구는 `.env` 모드와 무관하게 항상 dry 트레이더를 쓴다.
   확인할 것: 알림 본문의 손절 참고선과 📥 메시지의 손절이 같은지, 명목 = 자본 × 배율인지(펀딩 게이트에 걸리면 절반), 보유 한도 시각이 사양(8시간·7일·20일)과 맞는지. 5분봉 사례가 "보류"로 끝나면 그 시각의 4시간봉이 상승 배열이었던 것이다.
3. 화면 확인. 백오피스 '자동매매' 화면 아래 "Binance 선물 자동매매 — 포지션" 표에 열린·닫힌 포지션이 KST 시각으로 나온다(도구가 지운 확인용 행은 안 보인다).
   상시 운영 뒤 실제 신호가 오면 같은 형식의 📥/📤 가 오고 표에 남는다. dry 로 1~2주 운영해 표본 성과(3.5절)와 비슷한지 본 뒤 live 로 간다.

## 4. `AUTOTRADE_MODE` 상세 — 공용 가상 장부와 계정별 live

실행기 하나가 장부 하나다. 엔진은 **공용 가상 장부** 실행기를 늘 만들고, `.env` `AUTOTRADE_MODE=live` 일 때만 **계정별 live 실행기**를 더한다.
코드 배포·업데이트만으로는 절대 실제 주문이 나가지 않는다.

| 장부 | 언제 | 브로커 | 정책 | `alert_orders` | 알림 |
|---|---|---|---|---|---|
| 공용 가상 장부 | 항상 (`off`·`dry`·`live`) | `DryRunBroker` (API 호출 없음, 접수 즉시 가상 체결) | 구조 검사만 — 정규장·수량·미결 중복·보유 여부. 스위치·종목 체크·금액·보유 수·횟수·손실·잔고 한도 없음 | `mode=dry`, `account_id` NULL | 공용 채널 `[DRY]` 매수 체결 + 청산 완료·오늘 가상매매 성적 (주문 접수·매도 체결은 같은 내용이라 보내지 않는다) |
| 계정 live | `AUTOTRADE_MODE=live` + 그 계정 토스 live 스위치 ON | 그 계정 키의 `TossOrderClient` (실제 `POST /api/v1/orders`) | 전체 — 계정 스위치·종목 자동·한도(계정마다 집계)·매수가능금액 | `mode=live`, `account_id` = 계정 | 그 계정 텔레그램: 주문 접수/체결(실현손익)/실패/차단 + 장 마감 오늘 성적 |

### 4.1 실제 주문이 나가는 조건

1. `AUTOTRADE_MODE=live` (`.env`, 엔진 재시작 필요)
2. 계정이 백오피스 '내 API 키' 에 **토스 키와 텔레그램 키**를 저장하고, '자동매매' 화면의 **내 live 매매 → 토스 live** 를 켰다 (재시작 불필요, 엔진이 사이클마다 반영)
3. 해당 종목의 **자동매매 대상 체크 + 1회 매수 금액 > 0** ('종목' 화면, 관리자). 금액은 계정의 **금액 배율**을 곱한다

스위치가 꺼졌거나 종목이 자동매매 대상이 아니면 그 계정은 계좌 조회 없이 넘어간다. 한도에 걸리면 의도가 `rejected` 로 기록되고 사유가 남는다.

### 4.2 공용 가상 장부가 하는 일

- 확정 매수 신호마다 지정가(신호가 +0.3%) 가상 매수 → 접수 즉시 체결로 기록되고, 사이클 끝의 미결 추적에서 `filled` 가 된다. 금액은 종목 금액, 없으면 `VIRTUAL_AMOUNT`, 한 주가 더 비싸면 1주.
- **가상 체결이 엔진의 보유다**: 체결된 가상 의도를 누적한 모의 보유(`db.dry_positions`, 매수는 가중 평단·매도는 수량 차감)만 엔진이 보유로 본다 — 실계좌는 읽지 않는다.
  그래서 산 종목은 '보유' 로 관리되어 손절·매도·익절·마감 정리 신호에 전량 시장가 가상 매도가 나가고, 보유가 사라지면 청산 완료(`※ 가상 장부 체결가 기준`)와
  `trade_log.csv`, 장 마감 `📈 오늘 가상매매 성적` 까지 이어진다. 재시작해도 DB 의 체결 기록에서 다시 계산된다.
- 잔고는 무한대로 본다. 수수료·슬리피지는 없다 — 규칙대로 사고팔았을 때의 결과를 보는 모의매매다. 백오피스 '자동매매' 화면의 '공용 가상 장부' 가 현재 모의 보유와 가상 주문이다.
- **live 로 가기 전** 가상 장부 기록을 '매매 결과' 화면에서 검토한다.

### 4.3 live 에서 주문이 만들어지는 방식

- 매수: 신호가 × (1 + `AUTOTRADE_BUY_BUFFER_PCT`%) 지정가(호가 단위 보정), 수량 = 1회 매수 금액 × 계정 배율 ÷ 지정가 (내림, 1주 미만이면 거절).
  `AUTOTRADE_BUY_TTL_MIN` 안에 미체결이면 취소. 같은 신호봉으로는 한 번만.
- 매도: 🔴 손절/매도 · 🟢 전량 익절 · 🟠 마감 정리 신호에 **그 계정 계좌의** 매도가능수량 전량 **시장가**. 미결 매수가 있으면 먼저 취소.
  불타기(추가매수)·일부 익절(절반·1/3)은 알림만 낸다. 청산 신호는 가상 장부가 판 뒤 다시 오지 않으므로, 계정 매도가 실패하면 🚫 알림을 보고 직접 확인한다.
- `clientOrderId` 멱등키(의도 ID)를 보내 재시도·재시작으로 같은 주문이 두 번 나가지 않는다.
- 자동 차단: 주문 실패 3회 연속, 또는 `prerequisite-required`(약관·교육 미완료) → **그 계정의 토스 live 스위치**를 끄고 ⛔ 알림.
- 정규장 봉·정규장 시간에만 주문한다. 한국 NXT 시간외, 미국 프리·애프터마켓은 제외.
- 스위치를 꺼도 미결 live 주문이 남은 계정은 추적(TTL 취소·체결 기록)이 끝날 때까지 실행기를 유지한다.

### 4.4 사전 조건과 전환 순서

1. 각 계정 소유자가 토스 WTS 에서 **약관 동의·교육 이수·위험 고지**를 완료하고, **허용 IP 관리에 서버 공인 IP** 를 등록한다.
2. 백오피스 '내 API 키' 에 토스·텔레그램 키를 저장하고 **연결 확인**(계좌 + 매수가능금액, 텔레그램 테스트 발송)이 성공해야 한다.
3. 관리자가 `.env` 에 `AUTOTRADE_MODE=live` → 엔진 재시작. 한도(3.4)를 먼저 작게 잡는다.
4. 계정이 '자동매매' 화면에서 금액 배율을 정하고 토스 live 를 켠다. 문제가 생기면 끈다(즉시, 재시작 불필요). 관리자는 '계정' 화면에서 누구의 live 든 끌 수 있다. 미결 주문은 표에서 수동 취소할 수 있다.

주문 코드는 `alertbot/trading/broker.py` 에만 있다. `toss_client.py` 는 GET 만 한다. 계정 키는 백오피스 입력 → 암호화 저장 → live 워커 메모리에서만 풀린다(로그·화면·DB 평문 없음).

`run.py` 하나가 **엔진·Binance 워커·매크로 수집·백오피스** 네 서비스를 자식 프로세스로 띄우고 지킨다.

```powershell
cd C:\workspace\personal\finance-integration

.venv\Scripts\activate

```

**1. `.env` 작성 (3.1)**

- 토스 허용 IP 에 이 PC 의 공인 IP 를 등록한다.
- 백오피스: `ALERT_ADMIN_EMAIL`(첫 관리자 구글 이메일), `OAUTH_GOOGLE_CLIENT_ID`·`SECRET`, `OAUTH_GOOGLE_REDIRECT_URL`(예: `http://127.0.0.1:8000/auth/callback` — Google 콘솔의 승인된 리디렉션 URI 에 같은 주소 등록),

## 6. 배포 — Ubuntu (Docker)

요구사항: Docker Engine + Compose 플러그인, MySQL 접근, 서버에서 나가는 인터넷(5절과 같은 API). 이미지는 `python:3.12-slim` 기반이고,
컨테이너 하나(`alertbot`)에서 `run.py` 가 엔진·Binance 워커·매크로 수집·백오피스를 띄운다.

```bash
git clone <repo> alertbot && cd alertbot
cp /path/to/.env .env                 # 3.1 의 키 (FRED 키 포함). 파일 권한: chmod 600 .env
mkdir -p data                         # 로그·CSV 볼륨
docker compose down --remove-orphans  # 예전 3개 서비스(engine·backoffice·binance) 구성에서 넘어올 때 한 번 — 안 하면 옛 컨테이너가 남아 알림·주문이 두 번 나간다
docker compose up -d --build
docker compose logs -f alertbot       # [engine] "엔진 시작"·"장 운영 KR/US ... (캘린더)", [binance] "Binance 감시 시작", [macro] "매크로 수집 시작 — … FRED on"
docker compose exec alertbot python -m alertbot.macro backfill   # 처음 한 번 — 매크로 홈 3년치
docker compose exec alertbot python -m alertbot.macro status
docker compose exec alertbot python run.py status                # 네 서비스 running
```

- 토스 허용 IP 에 **서버의 공인 IP** 를 등록해야 한다. 등록 전엔 403 으로 엔진이 종료된다.
- 백오피스는 `127.0.0.1:8000` 에만 공개되고, 들어가려면 Google 로그인(허용 계정)이 필요하다. 밖에서 보려면 `ssh -L 8000:127.0.0.1:8000 user@server` 로 터널을 열고
  `OAUTH_GOOGLE_REDIRECT_URL` 의 주소(예: http://127.0.0.1:8000)로 접속한다. 도메인·HTTPS 리버스 프록시로 열면 `OAUTH_GOOGLE_REDIRECT_URL=https://…/auth/callback` 으로 바꾸고 Google 콘솔에도 같은 주소를 등록한다.
  `OAUTH_GOOGLE_CLIENT_ID`·`OAUTH_GOOGLE_CLIENT_SECRET`·`OAUTH_GOOGLE_REDIRECT_URL`·`ALERT_ADMIN_EMAIL`·`ALERT_MASTER_KEY` 중 하나라도 없으면 백오피스만 재시작 대기에 머문다.
- FRED 키는 `.env` 파일에 두면 된다. 환경변수로만 줄 때는 `ALERT_FRED_API_KEY` 이름이어야 한다(`FRED_API_KEY` 는 `.env` 파일에서만 읽는다).
- 매크로 수집은 Yahoo Finance·일본 재무성(mof.go.jp)·FRED 로 나간다. 방화벽이 막으면 해당 작업만 실패로 남고(홈의 빨간 칩·매크로 관리 '수집 작업') 나머지 서비스는 영향이 없다.
- 가상 장부 전환 1회 작업(5절)은 `docker compose exec alertbot python run.py stop engine`·`… stop binance` 뒤 `docker compose exec alertbot python -m alertbot.db reset-paper`, 끝나면 `… start engine`·`… start binance`.
- MySQL 이 같은 서버에 있으면 `.env` 의 `MYSQL_HOST` 를 호스트 IP(예: `172.17.0.1`)로 두거나 compose 에 `extra_hosts: ["host.docker.internal:host-gateway"]` 를 추가하고 `host.docker.internal` 을 쓴다.
- 데이터: `./data/` 에 로그와 CSV 가 남는다(매크로 시계열은 MySQL). `.env` 는 이미지에 들어가지 않고 `env_file` 로 주입된다. 로그는 `docker compose logs` 로도 본다(매크로·백오피스는 여기에만).
- 운영 명령:

```bash
docker compose exec alertbot python run.py restart macro    # 서비스 하나만 재시작 (백오피스 '운영' 화면과 같다)
docker compose restart alertbot      # .env 변경 반영 (예: AUTOTRADE_MODE, FRED 키) — 전부 재시작
docker compose up -d --build         # 코드 업데이트 후 재빌드 (git pull 뒤). 새 run_*.py 는 Dockerfile 의 COPY 에 있어야 한다
docker compose down                  # 중지 — 워커가 사이클을 마칠 때까지 기다린다 (stop_grace_period 150초)
```

`restart: unless-stopped` 라 서버 재부팅 후 자동으로 올라온다. Docker 는 이 문서를 만든 개발 PC 에 설치되어 있지 않아 실제 빌드 검증은 하지 않았다.

- 키를 지우면 그 공급자의 live 가 꺼지고, 텔레그램 키를 지우면 모든 live 가 꺼진다. live 를 켜려면 해당 키와 텔레그램 키가 있어야 한다(알림 없는 실매매 금지).
- 자기 자신과 `ALERT_ADMIN_EMAIL` 계정은 중지·강등할 수 없다(기동 때 관리자로 되돌린다).
- 옛 주소 `/summary`(시황) 와 `/channels`(채널)는 각각 상태·알림 탭으로 넘어간다.

주문 의도 상태: `proposed`(검사 전) → `rejected`(정책 거절, 사유 기록) / `sent`·`open`(접수·대기) → `filled` / `partial` / `canceled`(TTL·수동·매도 전 취소) / `failed`(브로커 오류).

**키 보관** — 계정 키는 공급자 필드 JSON 통째로 AES-256-GCM 으로 암호화해 `alert_account_keys` 에 둔다(계정·공급자를 인증 데이터로 묶어 행을 옮기면 복호화 실패).
마스터 키는 `.env` `ALERT_MASTER_KEY` 에만 있으니 DB 덤프가 새도 키는 안전하다 — 대신 `.env` 와 DB 백업을 한곳에 두지 않는다. 텔레그램 통신 오류 문구의 봇 토큰은 가려서 이력에 남긴다.

장단기 역전은 정보색(파랑), 역전 해소는 경고색. 미·일 10년 금리차 2.20/1.80/1.50%p 이하는 캐리 여유 주의/경계/위험. 임계는 `alertbot/macro/scoring.py`.

**시나리오 구간·기본 확률** — 사람이 넣는 값이 없다. 최근 3년 SOXX 일수익률에서 추세를 빼고 남은 거래일만큼 복원추출해
연말 가격 분포를 만든 뒤 등확률로 넷을 자른다(자를 때는 네 경로가 25% 씩). **구간은 그대로 두고 확률만 매시간 다시 센다** —
매일 다시 자르면 늘 25% 로 돌아가 아무것도 말해 주지 않는다. 가격이 구간 밖으로 나가거나 해가 바뀌면 다시 잡고,
그 스냅샷은 `alert_settings.macro_bands` 에 있다. 로그정규 대신 실제 수익률을 섞어 꼬리가 두껍지만, 변동성 군집은 담지 못해 양 끝 구간은 여전히 과소평가다.

**시나리오 확률** — 그 기본 확률에 판별 지표 신호를 로그 오즈로 더해 기울인다: `p ∝ base · exp(0.30 · Σ w·s·A)`.
신호는 임계 사이를 잇는 연속값이다(±1 로 튀지 않는다): 미 근원 CPI(2.2 ↔ 2.7%), 일본 근원 CPI(2.0 ↔ 2.5%),
EPS 추정치 30일 변화(×2, +5% 에서 최대 · ±0.5% 안이면 '상향 중단' 경고), SOXX/SPY 상대강도(50일선·20일 기울기 / 52주 상대 저점),
DRAM 30일 변화(×2, ±10% 에서 최대), FOMC·BOJ 결과 플래그(구간을 잡은 날 이후 것만).
값이 없는 지표는 빠진다(미반영). 하루 한 번 `alert_macro_scenario_log` 에 남긴다.
분석 프레임이지 예측·자문이 아니다.

## 8. 텔레그램 설정

채널은 둘이다. **공용 채널**은 `.env` `TELEGRAM_PUBLIC_BOT_TOKEN` / `TELEGRAM_PUBLIC_CHAT_ID` 로, **계정 채널**은 각 계정이 백오피스 '내 API 키 → 텔레그램' 에 봇 토큰과 채팅 ID 를 넣어 만든다.

1. BotFather 에서 봇을 만들고 토큰(`1234567890:AA...`)을 받는다.
2. 받는 사람이 봇 대화방을 열고 **시작(/start)** 을 누른다. 봇은 먼저 말을 건 상대에게만 보낼 수 있다.
3. 채팅 ID 를 조회한다 (봇 자신의 ID 를 넣으면 `can't send messages to the bot` 오류). `<TOKEN>` 자리에 봇 토큰을 넣는다:

```bash
python -c "import requests, sys; print(requests.get(f'https://api.telegram.org/bot{sys.argv[1]}/getUpdates', timeout=10).json())" <TOKEN>
```

4. 공용 채널은 백오피스 '알림' 의 테스트 발송(관리자), 계정 채널은 '내 API 키' 의 연결 확인으로 확인한다.

## 9. 문제 해결

| 증상 | 원인 · 조치 |
|---|---|
| 기동 직후 `403 — 허용 IP 미등록` 종료 | 토스 WTS > Open API > 허용 IP 관리에 실행 PC/서버 공인 IP 등록 (공용 키). 계정 키면 그 계정 텔레그램에 `⛔ live 준비 실패` 가 오고 10분마다 다시 시도 |
| 백오피스가 `.env 에 … 가 없다` 로 종료 | `OAUTH_GOOGLE_CLIENT_ID/SECRET`·`ALERT_ADMIN_EMAIL`·`ALERT_MASTER_KEY` 를 넣는다 (3.1) |
| 구글 로그인 `redirect_uri_mismatch` | `.env` 의 `OAUTH_GOOGLE_REDIRECT_URL` 과 Google 콘솔의 승인된 리디렉션 URI 를 글자 그대로(http/https·localhost/127.0.0.1·포트·경로) 맞춘다. 보내는 값은 백오피스 시작 로그에 찍힌다 |
| 구글 로그인 뒤 `로그인 요청이 만료됐거나 일치하지 않는다` | 로그인을 시작한 주소와 리다이렉트 URL 의 호스트가 다르다(localhost ↔ 127.0.0.1). `OAUTH_GOOGLE_REDIRECT_URL` 의 주소로 접속해 다시 로그인 |
| 로그인 뒤 `허용된 계정이 아니다` / `등록된 구글 계정과 다른 계정이다` | 관리자가 '계정' 에 그 이메일을 추가·재개한다 / 처음 로그인한 구글 계정으로 들어온다 |
| '내 API 키' 에 `복호화 실패` | `ALERT_MASTER_KEY` 가 저장 때와 다르다. 원래 키로 되돌리거나 키를 다시 입력한다 |
| `텔레그램 전송 실패: chat not found` | `TELEGRAM_CHAT_ID` 가 채팅 ID 가 아니거나 수신자가 `/start` 를 안 눌렀다 |

| `the bot can't send messages to the bot` | 채팅 ID 자리에 봇 ID 를 넣었다 |
| 백오피스 heartbeat 경고 | 엔진이 꺼졌거나 MySQL 연결 실패. '운영' 화면의 엔진 상태·마지막 출력과 엔진 로그 확인 |
| `다른 run.py 가 이미 돌고 있다` 로 시작 거부 | 다른 창·서버의 `run.py` 가 돌고 있다(`python run.py status`). 강제로 끈 직후면 30초 뒤 다시 실행 |
| 운영 화면 `run.py 가 돌고 있지 않다` | 백오피스만 따로(`run_backoffice.py`) 떠 있거나 관리 프로세스가 죽었다. `python run.py` 로 실행 |
| 로그·신호 이력의 `⚪ 시스템 … 비정상 종료했다 (연속 N회)` | 운영 화면의 마지막 출력에서 사유 확인(토스 403·.env 누락 등). 5·30·120·300초 간격으로 계속 다시 켠다 |
| `heartbeat 가 N분째 없다 — 멈춘 것으로 보고 다시 켠다` | 워커가 응답 없이 멈췄다(네트워크·DB 대기 등). 자동으로 재시작된다. 반복되면 워커 로그 확인 |
| 코인 급변 알림이 너무 많다/적다 | `config.SCAN_ATR_MULT`(기준 10.3, 올리면 줄어든다). 특정 코인은 종목 화면에서 뺀다 |
| `MySQL 연결 재수립 후 재시도` 경고 | 서버가 놀던 연결을 끊은 것. 자동 복구되며 정상 |
| `캘린더 ... 고정 시간으로 판단한다` | 캘린더 API 실패. 고정 시간(KR 09:00~15:30, US 09:30~16:00)으로 동작 |
| 주문 권한 확인 → `사전 자격 미충족` | 토스 WTS 에서 약관 동의·교육 이수·위험 고지 완료 후 재확인 |
| ⛔ 자동매매 차단 알림 (계정 텔레그램) | 연속 실패 또는 권한 오류. '자동매매' 표의 사유를 확인하고 내 live 스위치를 다시 켠다 |
| 홈에 `데이터 없음 — 백필 필요` · 스파크라인·등급이 비어 있다 | 백필을 안 했다. `python -m alertbot.macro backfill` (Docker 는 `docker compose exec alertbot …`) |
| 홈의 `EPS 추정치` 칩이 빨갛다 · `Invalid Crumb` | Yahoo 크럼이 만료됐다. 다음 주기(12시간)에 새로 받아 다시 시도한다. 계속되면 `python run.py restart macro` |
| 홈의 `DRAM 현물가` 칩이 빨갛다 | 집계 JSON 과 DRAMeXchange 가 둘 다 막혔다. 다음 주기(3시간)에 다시 시도하며, DRAM 지표만 '수집 대기'로 빠진다 |
| BOJ 결정 결과가 회의 다음 날에도 비어 있다 | BIS 정책금리가 며칠 늦게 올라온다 — 값이 들어오면 인상·인하·동결이 자동으로 채워진다 |
| 홈의 `미 금리(FRED)` 칩이 빨갛다 · `FRED_API_KEY 가 없어 건너뜀` | `.env` 에 `ALERT_FRED_API_KEY`(또는 `FRED_API_KEY`)를 넣고 `python run.py restart macro` |
| 홈의 `시세(Yahoo)`·`JGB(MOF)` 칩이 빨갛다 | 외부 사이트 일시 오류·차단. 칩에 마우스를 올리면 사유, 다음 주기(10분·60분)에 다시 시도한다. 계속되면 서버 방화벽의 나가는 연결 확인 |
| 홈의 미 기준금리가 FOMC 직후 옛 범위다 | FRED 는 결정 다음 날 반영한다. 매크로 관리에서 그 FOMC 이벤트 결과에 `→ 3.75~4.00%` 처럼 범위를 적으면 바로 반영된다 |
| 레이트리밋 경고(429) | 자동 대기·재시도. 반복되면 `MIN_CALL_GAP_SEC` 을 늘린다 |
